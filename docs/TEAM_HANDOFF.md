## 最后如何比较效果

以下是建议的比较协议，具体测试种子和预算需要在最终评估前共同确定并提交记录：

- 两条路线使用相同的最终评估环境版本、场景配置、奖励定义、动作与观测接口、步数上限及成功判定。若方法需要不同输入表示，应从同一环境信息转换；改变任务本身的方案需要单独比较。
- 原三个场景用于检查已有能力是否保留；全部 33 个训练场景用于检查训练覆盖；最终优劣主要依据双方均未用于训练、调参或选模型的独立测试场景。
- 开发阶段使用训练集和验证集，双方先固定候选模型及其哈希，再运行同一批最终测试场景。最终测试反馈若用于改进，就需要另设新的最终测试集。
- 主要比较采摘成功率，同时记录损伤率、超时率、回报、成功回合步数、推理耗时及失败原因。失败和重置报错不能从统计中悄悄删除。不要仅凭原三个场景成功或单次最高回报判断优劣。
- 尽可能采用一致的训练预算和多个训练随机种子。至少记录训练交互次数、梯度更新数、示范数据量、运行时间和硬件；不同方法或硬件下，单凭更新次数或耗时无法证明资源投入相同。资源不同的结果应明确标注。
- 最终评估冻结模型，不在线训练，不人工替换动作；保存逐场景结果，用同场景配对比较并报告不确定性。场景缓存需保持轨迹等价；计时比较要使用一致的缓存条件，并区分冷启动与缓存命中。

## 场景缓存与分段计时

可选的 `CertifiedSceneCache` 保存通过有效性检查的、由种子确定的场景初始状态及随机数生成器状态，并保留原始 `reset` 返回信息。`last_reset_profile` 单独记录本次实际执行的有效性检查工作；缓存命中时，新增检查调用次数和动作数均为零，但返回信息中的历史 `reference_route_checks` 仍保留。

同一进程中重复评估时，需要复用同一个缓存对象。单次命令行运行若每个种子都不同，就不会获得缓存命中的收益；不同进程之间也不共享此缓存。接口示例和限制见实验 035 的 `RESULTS.md`。实测缓存已填充后的重复评估提速约 `2.84` 倍，计入首次填充成本后约 `1.80` 倍；这些数字仅适用于重复评估。缓存命中后，物理仿真是剩余耗时的主要来源。

评估和环境接口默认不开启缓存。要求每次重置都重新进行有效性检查的历史实验脚本，应继续关闭缓存。对于通过文件哈希固定版本的历史实验，应检出其原始 Git 提交进行复现，因为当前代码已经加入后续的缓存和计时修改。
